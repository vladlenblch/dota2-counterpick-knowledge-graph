# Вопросы к графу знаний

Пользователь пишет вопрос, а не выбирает CQ-файл:

```powershell
.\.venv\Scripts\python.exe -m dota_kg ask "кто контрит Фантом Лансера на миде"
.\.venv\Scripts\python.exe -m dota_kg ask "кто контрит ПЛ"
.\.venv\Scripts\python.exe -m dota_kg ask "что купить Rubick против ПЛ в поздней игре"
.\.venv\Scripts\python.exe -m dota_kg ask "почему Lion контрит Crystal Maiden" --format json
```

`questions.py` определяет задачу и распознаёт сущности. В `answers.py` есть ровно
один обработчик на каждый из 12 компетентностных вопросов README. Это обход RDF
через RDFLib с общей моделью ранжирования в `ranking.py`.
Один текстовый пример на каждую задачу хранится в `examples.json`.

Запускайте Python из `.venv`: команда `py` может выбрать другой установленный
интерпретатор без зависимостей проекта. Команда `ask` выводит только ответы; JSON в stdout остаётся пригодным для программного чтения.
Первый запуск читает исходный Turtle и сохраняет разобранные термы и связи в
`ontology/.cache/game.json`. Следующие запуски читают кэш. Его актуальность проверяется
по SHA-256 каталога и исходных RDF-файлов; при изменениях он перестраивается.
Повреждённый кэш можно удалить: он не содержит новых знаний и будет создан заново.

## Как выбирается ответ

Для контрпика используется цепочка из самого графа:

`герой → способность → эффект → механика ← правило → механика противника ← эффект/наблюдаемый признак`.

Вход содержит только условия вопроса: героя/противника, позицию, стадию,
способность или предмет, если они названы. Список кандидатов, нужная механика,
основания и ограничения не передаются пользователем и не зашиты в пример.
Ранжирование использует уточненные эффекты с `effectTarget`; общая разметка
сохраняется в графе для остальных задач. Ограничение собственных действий не считается
контролем противника. Разные основания одной механики являются альтернативами:
условие Scepter у одного основания не переносится на доступное без него.
При поиске развеивания учитываются условия самого развеивания, а не остальных
эффектов способности.

Авторские правила игры остаются в RDF и воспроизводимом экспорте онтологии.
Правило с `rulePurpose=compensate` компенсирует уязвимость собственного героя;
остальные правила используются для противодействия противнику.

## Ранжирование

Правила и веса находятся в `data/counter_rules.parquet` и экспортируются в
`CounterRule`: `ruleWeight`, `ruleFamily`, `sourceEffectTarget`. В логике расчета
нет списков контрпиков и коэффициентов для отдельных героев.

Для каждого противника из эффектов выводятся его игровые зависимости: например,
группа существ, восстановление здоровья, пассивная защита, активное применение
заклинаний. Основания сохраняют ссылки на исходные факты. Далее:

1. Проверяются получатель эффекта, условия и явно заданные предметы.
2. Вес правила уточняется по именованным параметрам: урону, длительности,
   перезарядке, развеиванию и другим доступным характеристикам.
3. В одной семье берется сильнейшее основание каждой способности: первая
   способность полностью, вторая с множителем 0.3, третья с 0.09.
4. Главная семья учитывается полностью, остальные с множителем 0.4. Повторное
   использование одной способности в разных семьях получает множитель 0.25.
5. Вычитается 0.2 механического преимущества противника. Статистическая поправка
   ограничена по модулю 0.1 и сглаживается числом матчей: `n / (n + 300)`.

Статистика не создает кандидата без механического основания. Процент побед и
число матчей не выводятся в текст и JSON. Балл не является вероятностью победы.
Позиция фильтрует героев, а не выбирает статистику отдельной линии. Используются
максимальные доступные значения параметров способностей; `--level` задает уровень
для оценки запаса здоровья (по умолчанию 18). Выбранный аспект, сборка, тайминг и
текущее состояние боя полностью не моделируются.

Предметы не предполагаются автоматически. Их можно указать явно, в том числе
несколько раз:

```bash
python -m dota_kg ask "кто контрит ПЛ на керри" --with-item "Battle Fury"
python -m dota_kg ask "почему Anti-Mage контрит Phantom Lancer" --enemy-item "Aghanim's Shard" --format json
```

`--with-item` задает предмет нашего кандидата, `--enemy-item` - противника.
Без этих параметров Scepter/Shard и купленные предметы не добавляют скрытые бонусы.
Текст контрпика показывает главное основание, JSON также содержит `score`,
`mechanical_score`, `reverse_score`, `reasons` с отдельными вкладами и ссылками на RDF.

`--limit 3` ограничивает число разных героев **на каждой позиции**, по умолчанию три.
В вопросах о прерывании, иллюзиях и обнаружении способности и предметы имеют
отдельные лимиты. При развеивании лимит действует отдельно для каждого эффекта и вида средства (способность или предмет).
Для покупок используется `item_ranking.py`: механический балл умножается на
совместимость с героем и соответствие стадии покупки. Совместимость выводится
из `ItemUsageObservation`: частоты покупки самим героем и сборок героев на той же
позиции с тем же типом атаки. Это общая статистика сборок, без разбиения по противнику.
Стадия оценивается по наблюдаемым покупкам `early`, `mid`, `late`. Если наблюдений
нет, поправка на стадию нейтральна. Отдельных таблиц предпочтений по ролям нет.

Обычные редкие покупки отсекаются. Ситуативный предмет может пройти при сильном
контрмеханическом основании и подходящем профиле покупателя. Частота сама по себе
не создает рекомендацию. Для известных сборок отсутствие покупки - ограничение
покрытия, а не доказательство невозможности ее использовать. Явно названный предмет
проверяется отдельно, даже если он редко встречается в сборках.

Числовые параметры уточняют полезность: шанс баша отличается от гарантированного
стана; промахи исключаются либо постоянно, либо на отдельной атаке; учитываются
величина брони и длительность эффекта. Уже имеющийся сильный cleave уменьшает
ценность дополнительного cleave. Урон по одной цели не считается уроном по области. Сопротивление замедлению
не считается замедлением противника. Специализированный активный предмет
не предлагается только ради побочного числового бонуса, если его основное действие не помогает.
Не предлагаются уже имеющиеся, бесплатные, нейтральные и непокупаемые предметы.
Недорогие компоненты только со статическими бонусами остаются для ранней игры,
компенсации уязвимостей и явной проверки. Список не заполняется покупками с одним
и тем же главным действием; он может содержать меньше заданного лимита.

Правила `rulePurpose=purchase` добавляют предметам защиту от атак и контроля,
развеивание отрицательных эффектов на союзнике и положительных на противнике,
блок направленного принудительного боя и противодействие группе существ. Они не участвуют в ранжировании героев. Данные и правила находятся в
тех же классах онтологии. JSON покупки содержит `score`, `mechanical_score`,
`suitability`, `timing`, `reasons`; итоговый балл равен произведению
`mechanical_score * suitability * timing`. При компенсации числовой уязвимости
поправка `suitability` также учитывает стоимость средства. Процент побед и число матчей не выводятся.

Позиции выбираются только из `mostPopularPosition` и `secondMostPopularPosition` героя:

| Позиция | Значение свойства |
| --- | --- |
| Керри | 1 |
| Мид | 2 |
| Офлейн | 3 |
| Поддержка | 4 |
| Полная поддержка | 5 |

Без ограничения выводятся варианты по всем пяти позициям. С указанной позицией
герой участвует в поиске, если она совпадает с основной или имеющейся дополнительной позицией.
У героев с основной позицией 1 дополнительная отсутствует; они рекомендуются только на керри.
Если обе позиции отсутствуют, герой не попадает в рекомендации контрпиков.
Оценки `carryLevel`, `nukerLevel`, `supportLevel` и другие игровые характеристики
не используются как запасной способ определения позиции.
«На саппорте» означает позицию 4, «на хард саппорте» или «на полной поддержке» - 5.
Поддерживаются также формулировки «на позиции 2», «на 4-й позиции» и `pos5`.
Для сопоставления сборок предметов используется сама позиция 1-5, а также
тип атаки героя. Если позиция не названа, берется `mostPopularPosition`.

## Имена, клички и пределы разбора

Английские имена берутся из графа. Есть небольшой словарь русских названий и
прозвищ: ПЛ/Фантом Лансер, фантомка/ПА, ЦМ, АМ, дровка, рубик, БКБ и другие.
Словарь задаёт только соответствие имени сущности графа, а не игровые ответы.
Поддерживаются частые падежные окончания; это не полноценная русская морфология.
Можно добавлять `kg:alternativeName` в переданный граф без изменения парсера.
Неоднозначное имя вызывает просьбу уточнить название.

Разбор локальный, по ключевым формулировкам 12 задач. Он не понимает произвольный
русский текст, сложные отрицания, составные вопросы и произвольное число героев.
Неизвестная задача или отсутствие обязательного героя вызывает понятное сообщение.
Сложные фразы могут распознаваться неточно: параметры доступны в JSON для проверки.
При отсутствии фактов возвращается «в размеченных данных вариантов не найдено».

Будущая векторизация может заменить распознавание формулировок и имён, сохранив
структуру `Question` и поиск по графу. Она не восполняет отсутствующие игровые факты.

## Покрытие и проверка

Объяснения и условия берутся из `CounterRule`, `Effect` и именованных параметров.
Развеивание требует явного `requiredDispel` и известной цели применения.
Его необходимая сила выводится из официального `dispellableCode`; это свойство
не смешивается с типом развеивания, которое накладывает сама способность.
Обычное обнаружение не предлагается против эффектов с `DETECTION_IMMUNITY`.
По принятому правилу BKB отсутствие явного прохода трактуется как false.
Владение BKB отличается от его активации: без сведений об активности вывод условный.
CQ11 различает невосприимчивость к эффектам, блок направленного заклинания
и отражение копии. Отражение не отменяет исходное заклинание. Учитываются
исключения в фактах конкретных способностей; универсальной модели любого предмета пока нет.
Улучшения читаются из описаний Scepter/Shard, связанных талантов, модификаторов
аспектов и рядов значений. Шаблоны описаний подставляют значения соответствующего
улучшения; нулевой базовый параметр не заменяет значение Scepter/Shard.
Все модификаторы таланта или аспекта сохраняются в JSON. Новые взаимодействия не выдумываются.
Для прерывания поддержания прямой контроль предпочтительнее контроля,
требующего отдельного игрового события; условия такого срабатывания выводятся явно.
Для уязвимостей пока размечена компенсация низкой брони. При сравнении средств
компенсации учитывается стоимость, включая дешевые компоненты брони. Пустой ответ по другим
уязвимостям означает недостаток правил, а не отсутствие слабостей.

```powershell
.\.venv\Scripts\python.exe scripts/check_competency_queries.py
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

Реальные ответы сохраняются в `data/reports/competency-answers.md`, JSON с URI,
основаниями, условиями и распознанными параметрами — в `competency-queries.json`.
Модульные тесты изменяют факты, правила и статистику, проверяя изменение ответа.

## SPARQL из VSCode и CLI

| Файл | Задача | Входные параметры |
| --- | --- | --- |
| `01_counterpicks.rq` | Ранжирование героев с главным основанием | `enemy`, необязательно `position` и `hero` |
| `02_explanations.rq` | Балл и основное объяснение конкретной пары | `hero`, `enemy` |
| `03_conditions.rq` | Условия эффектов способности или предмета | `subject` |
| `05_illusions.rq` | Способности и предметы против группы существ | `enemy`, необязательно `hero` |

```bash
python -m dota_kg query queries/01_counterpicks.rq --bind "enemy=Phantom Lancer" --bind position=3
python -m dota_kg query queries/02_explanations.rq --bind "hero=Axe" --bind "enemy=Phantom Lancer"
python -m dota_kg query queries/03_conditions.rq --bind "subject=Shackleshot"
python -m dota_kg query queries/05_illusions.rq --bind "enemy=Phantom Lancer"
```

`--bind` передает RDF-термы через `initBindings`, без подстановки текста запроса.
Имена и клички разрешаются по графу, числа имеют числовой тип; можно передать URI.
`--with-item`, `--enemy-item` и `--level` доступны и для SPARQL. В запросе 05
`hero` ограничивает способности героя и задает владельца для проверки покупки;
без него выводятся общие средства противодействия, без персональной оценки сборки.
Можно также передать `--bind position=4` и `--bind phase=late`.
Аргумент семейства у `fn:ownerScore` и связанных функций принимает коды через запятую.
В файлах нет имен героев: можно менять параметры, фильтры, сортировку и `LIMIT`.

Функции пространства имен `fn:` вызывают ту же модель RDFLib, что и `ask`.
Они возвращают балл и URI объясняющих фактов. SPARQL сохраняет цепочку
`Hero -> Ability/Item -> Effect -> Mechanic -> CounterRule -> Mechanic` и
проверяет ее по графу. Обобщенные зависимости противника доступны через небольшое
временное RDF-представление; исходная онтология от выполнения запроса не меняется.
Эти функции регистрируются на время команды `query`, поэтому ранжирующие запросы
выполняются через CLI, а не непосредственно в Protégé. Запрос 03 - обычный SPARQL.

В VSCode: **Terminal -> Run Task -> SPARQL: контрпики** или
**SPARQL: объяснение пары**. Задачи запрашивают имена и позицию. Задача
**SPARQL: текущий файл** сохраняется для произвольных запросов без параметров.
Поддерживаются форматы `table`, `json`, `csv`; для `CONSTRUCT` используется `turtle`.
`FROM` и `SERVICE` отключены: запросы работают только с локальным графом.
